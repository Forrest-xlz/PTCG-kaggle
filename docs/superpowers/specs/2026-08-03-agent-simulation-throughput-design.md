# Agent Simulation Throughput Benchmark Design

## Goal

Add a local CPU benchmark that runs two Kaggle-compatible Pokemon TCG agent submission archives against each other with multiple processes and reports completed games per second.

The script is configured by editing constants in the file. It does not expose a command-line argument interface.

## Inputs

- Two `submission.tar.gz` archives generated by the notebooks in `agents/`.
- The local official `cg` runtime directory.
- Direct configuration values for game count, worker count, warm-up games, maximum selections per game, and seat balancing.

Each submission must contain `main.py` and `deck.csv`. The benchmark uses the same one-argument last-callable selection rule used by the competition loader, so it measures the submitted entrypoint rather than an internal helper chosen specially for the benchmark.

## Architecture

Create one focused Python script under `agents/`.

The parent process will:

1. Validate configuration and safely extract both submission archives to temporary directories.
2. Validate the required files and both 60-card decks.
3. Start a process pool using the multiprocessing `spawn` context for cross-platform behavior.
4. Divide games among workers, balancing player order when enabled.
5. Aggregate results and print throughput and outcome summaries.

Each worker will:

1. Add the configured official runtime parent to `sys.path`.
2. Load each submission in an isolated namespace and select its competition entrypoint.
3. Reuse the loaded agents for every game assigned to that worker.
4. Run warm-up games before participating in the timed workload.
5. Run games sequentially inside the worker because the engine stores the active battle pointer in process-global state.
6. Always call `battle_finish()` after a successfully started battle.

Workers run independently in parallel. Threads are not used.

## Game Loop

For each selection:

- Inspect the observation to identify the player whose action is requested.
- Call the corresponding agent with the raw observation dictionary.
- Validate that the returned value is a list of legal option indices.
- Pass it to `battle_select()`.
- Stop when the engine reports a result or when the configured maximum selection count is reached.

Half the scheduled games place Agent A in player slot 0 and half place Agent B there when seat balancing is enabled.

## Measurements

Initialization and warm-up are reported separately from the timed simulation section.

The final report includes:

- configured and actual worker count;
- requested, completed, failed, and timed-out games;
- total timed wall-clock seconds;
- aggregate completed games per second;
- average game duration and average selection count;
- Agent A wins, Agent B wins, draws, and seat-aware win rates;
- error categories with a small number of representative messages.

The primary throughput metric is successfully completed games divided by parent-process wall-clock time for the timed workload. This captures real multiprocessing throughput, including inter-process scheduling and result collection, while excluding archive extraction and warm-up.

## Configuration

The script exposes a small constant block near the top:

```python
AGENT_A_ARCHIVE = Path(...)
AGENT_B_ARCHIVE = Path(...)
CG_PATH = Path(...)
NUM_GAMES = 1000
NUM_WORKERS = 8
WARMUP_GAMES_PER_WORKER = 1
MAX_SELECTIONS = 1000
BALANCE_SEATS = True
```

`NUM_WORKERS` is capped at the number of scheduled games. Engine and agent code may create their own native CPU threads, so the user may need to compare worker counts rather than always using every logical CPU.

## Error Handling

- Reject unsafe archive members, missing required files, invalid decks, and invalid runtime paths before starting workers.
- Convert per-game agent, engine, illegal-action, startup, and timeout failures into structured results instead of terminating the entire benchmark.
- Fail immediately if worker initialization cannot load the engine or either agent.
- Clean temporary extraction directories after the process pool exits.

## Verification

Verification will cover:

- Python syntax compilation;
- archive path-safety and required-file validation;
- a small two-process smoke benchmark using the two generated submission archives when those archives are available locally;
- result accounting: every requested game must appear exactly once as completed, failed, or timed out;
- seat allocation differs by at most one game when balancing is enabled.

The benchmark does not modify either submission archive.
